# MurderBoard 实现路线图

本文档将产品需求、技术规格和数据模型拆分为可实施阶段，帮助后续开发按稳定顺序推进。

## 阶段 1：项目基础

目标：建立可运行的应用骨架和基础工程规范。

交付内容：

- 选择前端、后端和持久化技术栈。
- 建立项目目录结构。
- 建立基础构建、测试和格式化命令。
- 配置基础数据访问层。
- 定义通用错误类型和 DateTime 序列化规则。

完成标准：

- 项目可以本地启动。
- 基础测试命令可运行。
- DateTime 输入输出格式明确。

## 阶段 2：领域模型与持久化

目标：落地核心实体和约束。

交付内容：

- 实现 `Workspace`、`Case`、`Character`、`Clue`、`Event`。
- 实现事件与人物、线索的关联表或关联结构。
- 实现剧本名称唯一约束。
- 实现同一剧本下案件名称唯一约束。
- 实现软删除字段和默认查询过滤。

完成标准：

- 无法创建重名剧本。
- 无法在同一剧本下创建重名案件。
- 默认查询不返回软删除数据。
- 时间字段以结构化 DateTime 保存。

## 阶段 3：剧本和案件管理

目标：完成最小可用的剧本与案件流程。

交付内容：

- 创建、列表、详情、更新剧本。
- 创建、列表、详情、更新案件。
- 案件状态管理。
- 归档案件。
- 基础错误提示。

完成标准：

- 用户可以创建剧本并在其中创建案件。
- 用户可以重命名剧本和案件。
- 用户可以归档案件。
- 名称冲突会被明确提示。

## 阶段 4：人物、线索和事件

目标：支持核心推理记录能力。

交付内容：

- 人物增删改查。
- 线索增删改查。
- 事件增删改查。
- 事件关联人物和线索。
- 时间线按 `occurredAt` 排序展示。

完成标准：

- 用户可以围绕案件记录人物、线索和事件。
- 时间线排序稳定。
- 事件关联只允许使用同一案件内的资源。

## 阶段 5：删除、撤销和回收站

目标：避免误删导致数据不可恢复。

交付内容：

- 软删除剧本、案件、人物、线索和事件。
- 删除后的撤销入口。
- 回收站列表。
- 从回收站恢复资源。
- 永久删除已软删除资源。

完成标准：

- 删除不会立即不可逆移除数据。
- 已删除案件可以恢复。
- 恢复时会处理名称冲突。
- 永久删除只能作用于回收站资源。

## 阶段 6：归档恢复

目标：实现符合业务要求的归档恢复。

交付内容：

- 归档案件列表。
- 从归档案件创建当前剧本下的新案件。
- 复制人物、线索、事件和关联关系。
- 生成新的案件和子实体标识。
- 恢复时校验案件名称唯一性。

完成标准：

- 归档恢复不会覆盖原案件。
- 恢复结果是当前剧本下的新案件。
- 子实体关联在新案件中保持一致。
- 名称冲突不会静默覆盖。

## 阶段 7：导入、复制和体验完善

目标：提升数据迁移和整理效率。

交付内容：

- 案件复制。
- 剧本内或剧本间移动与复制策略。
- 导入前预检名称冲突。
- 搜索和过滤。
- 空状态、错误状态和确认提示。

完成标准：

- 复制和导入复用统一校验逻辑。
- 冲突信息可被用户理解并处理。
- 常用列表支持基本搜索和过滤。

## 测试重点

- 剧本名称唯一性。
- 同一剧本下案件名称唯一性。
- DateTime 序列化、排序和比较。
- 软删除默认过滤。
- 回收站恢复和永久删除。
- 归档恢复创建新案件。
- 复制、导入和恢复时的名称冲突处理。
- 事件关联资源必须属于同一案件。

## 风险与注意事项

- 不要将剧情事件时间和系统操作时间混用。
- 不要用硬删除替代默认删除流程。
- 不要在归档恢复时直接修改原案件。
- 不要在名称冲突时自动覆盖已有数据。
- 不要让界面层各自实现重复校验逻辑，应集中在领域服务或写入服务中。
